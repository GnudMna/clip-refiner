# コメント規約

**以下のコメント規約に遵守することを必須とする。**

言語は**日本語**。識別子・型名はバッククォートで囲む（例: `RefineMode`）。技術用語（Polling, CSV など）は英語のまま使ってよい。

**文体はです・ます調にしない。** 常体（だ・である調）または体言止めで書く。

- 良い例: `加工して書き戻す` / `変更がない場合は更新しない` / `失敗時は元の文字列を返す`
- 悪い例: `加工して書き戻します` / `更新しません` / `返します`

**1行に複数の文を書く場合を除き、句点（`。`）は付けない。** 1行1文のコメントは体言止めまたは動詞の終止形で終える。

**括弧は全角の `（` `）` は使わず、半角の `(` `)` のみを使用する。**

- 良い例: `ポーリング時は前回と同じ内容をスキップ (変更なし)`
- 良い例: `適用する加工モード (RefineMode)`
- 悪い例: `ポーリング時は前回と同じ内容をスキップ（変更なし）`
- 悪い例: `適用する加工モード（RefineMode）`

**コロンは全角の `：` は使わず、半角の `:` のみを使用する。**

- 良い例: `失敗時: 元の文字列を返す`
- 良い例: `引数: clipboard, mode`
- 悪い例: `失敗時：元の文字列を返す`
- 悪い例: `引数：clipboard, mode`

- 良い例: `テキストが変更された場合のみクリップボードを更新し、その内容を返す`
- 良い例 (1行に複数文): `変更を検知する。ポーリング時は前回と同じ内容をスキップする。`
- 悪い例: `テキストが変更された場合のみクリップボードを更新し、その内容を返す。`

## セクション区切り

ファイル内の論理ブロックの前に、次の形式で区切る:

```rust
// ======================================================================
// セクション名
// ======================================================================
```

例: `定数`, `パブリック関数`, `プライベート関数`, `テスト`

## ドキュメントコメント (`///`)

公開 API・主要な非公開関数・型・enum バリアント・構造体フィールドに付ける。

### 公開関数 (`pub fn`)

**`pub fn` には次の構成を必須とする。** `pub(crate)` や非公開関数は同構成を推奨するが必須ではない。

1. 1行目: 何をするか（要約）
2. 空行
3. 補足説明（必要な場合のみ）
4. `# Arguments` — 引数が 1 つ以上ある場合は必須 (`self` / `&self` / `&mut self` を含む)
5. `# Returns` — 戻り値の型 (`->`) がある場合は必須

引数がない場合は `# Arguments` を省略してよい。戻り値が `()` で暗黙の場合も `# Returns` を省略してよい。

`# Arguments` と `# Returns` の間、および補足説明と `# Arguments` の間には空行 (`///` のみの行) を 1 行入れる。

### その他の関数

**関数の構成:**

1. 1行目: 何をするか（要約）
2. 空行
3. 補足説明（必要な場合のみ）
4. `# Arguments` / `# Returns` セクション（引数・戻り値がある場合）

```rust
/// クリップボードのテキストを取得し、指定されたモードで加工して書き戻す
///
/// テキストが変更された場合のみクリップボードを更新し、その内容を返す
///
/// # Arguments
/// * `clipboard` - `arboard::Clipboard` のミュータブルなインスタンス
/// * `mode` - 適用する加工モード (`RefineMode`)
///
/// # Returns
/// * `Option<String>` - テキストが加工された場合は `Some(加工後テキスト)` を返し、
///   変更がなかった場合や空の場合は `None` を返す
```

**型・enum:** 役割を説明し、バリアントには1行で挙動を書く。副作用や失敗時の挙動も明記する（例: `失敗した場合は元のテキストを維持する`）。

**モジュール (`//!`):** モジュールの責務を2〜3行で説明する（`tray/mod.rs` 参照）。

## インラインコメント (`//`)

自明な処理には書かない。次の場合のみ使う:

- 非自明なビジネスロジック・エッジケース（例: 自身の書き戻しを無視）
- アルゴリズムの意図・手順
- UI 組み立ての段階
- テスト内の検証ステップ

## `unsafe` の根拠

`unsafe` ブロック・`unsafe impl` の直前には `// SAFETY:` で、その操作が安全である理由 (ポインタの有効期間・ハンドルの所有・サイズの前提など) を書く。`clippy::undocumented_unsafe_blocks` で強制する。

`unsafe fn` には `/// # Safety` で呼び出し側が守る条件を書く。

```rust
// SAFETY: `wide` は NUL 終端の UTF-16 で、呼び出し中は生存する
let handle = unsafe { CreateFileW(PCWSTR(wide.as_ptr()), /* ... */) };
```

## テスト

- セクション区切り `// テスト` を使う
- `#[test]` 関数には `///` で検証内容を書く
- **1 行目は `〜すること` で終える** (例: `空文字列は加工対象外とすること` / `英数字を URL エンコードできるようにすること`)
- `〜テスト` / `〜こと` (単独) / `〜と確認すること` などの別形式は使わない
- 補足説明が必要な場合は 2 行目以降に書き、**要約行 (1 行目) だけ** `〜すること` を満たせばよい
- テスト本体では、各アサーション群の意図を `//` で簡潔に補足する

```rust
// ======================================================================
// テスト
// ======================================================================

/// 空文字列は加工対象外とすること
#[test]
fn empty_text_is_not_processed() { /* ... */ }

/// ポーリング時は同一テキストをスキップし、イベント時は再処理すること
///
/// イベント駆動時は加工済みテキストの再コピーも対象とする
#[test]
fn polling_skips_unchanged_text() { /* ... */ }
```

## 書かないこと

- コードを読めば分かる処理の説明
- です・ます調の丁寧語（`します` / `です` / `ません` など）
- 1行1文なのに末尾に付けた句点（`。`）
- 全角括弧 `（` `）`（半角の `(` `)` を使う）
- 全角コロン `：`（半角の `:` を使う）
- 英語と日本語の混在した冗長なコメント
- セクション区切りなしの長大なファイル
